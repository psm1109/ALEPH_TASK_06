# 카드 5 — 설명서로 묶고, 잠근 앱으로 5일 써 보기

이 문서는 카드 1~4의 인증 구현, 로그인 공격 방어, 실제 사용 기록을 한 제출문으로 묶는 최종 문서다. 비밀번호·access token·refresh token·CAPTCHA 토큰·비밀키의 원문은 기록하지 않고 `[가림]`으로 표시한다.

## ① 무엇으로 붙였나

- 인증: Supabase Auth 이메일·비밀번호
- 브라우저 인증 클라이언트: `@supabase/supabase-js` `2.116.0`
- 인증 요청 보호: 브라우저가 AES-256-GCM 암호문을 만들고 RSA-OAEP-256으로 AES 키를 감싼 뒤 `auth-gateway`에 보낸다.
- 자동화 방지: 로그인·가입 화면의 Cloudflare Turnstile 토큰을 `auth-gateway`가 Supabase Auth로 전달하고, Supabase Auth가 서버에서 검증한다.
- 반복 로그인 방어: 운영 Supabase의 로그인·가입 Rate Limit을 IP당 `10 requests/5 min`으로 낮추고, 별도로 `auth-gateway`가 계정·IP의 서버 HMAC 식별자를 사용해 비밀번호 실패 횟수별 재시도 제한을 강제한다.
- 사람 식별: Supabase 세션의 JWT와 `auth.uid()`
- 자료 보호: `diary-data` Edge Function과 PostgreSQL RLS의 `user_id = auth.uid()`
- 세션 폐기: `auth.sessions` 확인을 `pgrst.db_pre_request`와 RLS에 함께 적용한다.
- 계정 삭제: `account-delete` Edge Function이 인증된 사용자만 자기 Auth 계정을 삭제하며, 자료의 `on delete cascade`로 연결 자료도 함께 삭제한다.

## ② 왜 그걸 골랐나

기존 T06이 Supabase PostgreSQL과 REST API를 사용하므로 계정, 세션, RLS를 같은 서비스 경계에서 연결할 수 있다. 비밀번호 해싱·세션 발급·세션 폐기를 직접 구현하지 않아도 되고, 사용자별 행 소유권을 `auth.uid()`로 데이터베이스에서 검사할 수 있어 선택했다.

직접 만든 Node.js 인증 서버는 해싱·세션 만료·중복 계정·배포를 모두 별도로 책임져야 하므로 현재 범위에서는 선택하지 않았다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 화면·브라우저 | 서버·자료 경계 |
| --- | --- | --- |
| 가입 | `public/index.html`의 `signup-form` → `public/app.js`의 `handleSignupSubmit` | `auth-gateway`의 `signup` → Supabase Auth 사용자 생성 |
| 로그인 | `login-form` → `handleLoginSubmit` → `requestProtectedAuth` | `auth-gateway`의 `login` → 세션 토큰 반환 → `state.session` 저장 |
| CAPTCHA | 로그인·가입 폼의 Turnstile 위젯 → 일회용 `captcha_token` 전달 | Supabase Auth가 Turnstile Secret으로 토큰을 검증하고, 사용한 토큰은 화면에서 초기화 |
| 반복 실패 제한 | 서버의 `429`와 남은 시간을 받아 로그인 버튼에 카운트다운 표시 | `private.auth_login_throttle`에 계정·IP HMAC, 실패 횟수, 다음 허용 시각만 저장하고 3회부터 `2 → 5 → 15 → 30 → 60 → 120초`, 9회부터 15분 제한 |
| 로그아웃 | `logout-button` → `handleLogout` | Supabase `signOut({ scope: "local" })` → 세션 폐기 → 로그인 화면 |
| 자료 조회 | `connectAndLoad` → `supabaseRequest` | `diary-data` → Data API → `auth.uid()` 기반 RLS로 자기 행만 반환 |

추가로 `exportAllData`는 최신 자료를 다시 조회해 JSON 한 파일로 내보내고, `deleteAccount`는 `account-delete`를 호출한다. `supabase/schema.sql`의 Auth 외래키 `on delete cascade`가 계획·할 일·실행·회고 자료의 삭제를 연결한다.

## ④ 안 열리는 것을 확인한 기록

각 항목은 성공한 요청과 거절된 요청을 나란히 둔다. 토큰과 비밀번호는 `[가림]`으로만 기록한다.

| 확인 | 성공한 요청 | 거절된 요청 | 판정 |
| --- | --- | --- | --- |
| 로그인 전 자료 차단 | 로그인 후 `GET /functions/v1/diary-data/plan_versions?...` → `200` | Authorization 없는 같은 조회 → `401 Authentication required` | 실제 배포 확인 필요 |
| 로그아웃 즉시 폐기 | 같은 계정의 로그인 중 GET → `200` | 로그아웃 직후 같은 URL·같은 `[가림]` 토큰 GET → `403`, `42501` | 카드 3 운영 기록 있음 |
| 계정 간 읽기 | A 계정의 자기 `tasks?id=eq.[A]` → `200` | A 계정의 B 자료 GET → `404`, `PGRST116` | 카드 4 운영 기록 있음 |
| 계정 간 변경·삭제 | A 계정의 자기 자료 PATCH/DELETE → 성공 | A 계정의 B 자료 PATCH/DELETE → `404`, `PGRST116` | 카드 4 운영 기록 있음 |
| 소유자 위조·비로그인 | A 계정의 위조 헤더/쿼리 → A 자료만 반환 | B `user_id`를 본문에 넣은 POST → `403`, `42501`; 비로그인 POST → `401` | 카드 4 운영 기록 있음 |
| CAPTCHA 적용 | 올바른 Turnstile Secret을 등록한 뒤 운영 앱 로그인 성공 | 잘못된 Secret 사용 시 Supabase Auth 로그에 `invalid-input-secret` 기록 | 사용자 운영 확인 있음 |
| 반복 로그인 제한 | 허용 상태의 올바른 비밀번호 로그인 → 성공 | 틀린 비밀번호 반복 입력 → 서버 제한과 화면 카운트다운 적용 | 반복 실패 제한은 사용자 운영 확인 있음; 전체 3~9회 단계별 수치와 성공 초기화는 별도 재검증 필요 |

계정 삭제의 별도 최종 확인은 실제 배포 후 `전체 자료 내보내기`로 백업하고 `계정 삭제`를 누른 뒤 로그인 실패와 자료 삭제 또는 삭제 안내를 확인해 이 표에 응답을 추가한다. 현재 저장소에는 서버 경로와 화면 안내를 구현했지만, 이 운영 확인은 아직 실행하지 않았다.

점진 제한의 첫 운영 배포에서는 PostgREST 사전 요청 함수의 `service_role` 권한이 빠져 제한 RPC가 `403`, PostgreSQL `42501`로 거절됐다. `service_role`에 `private` 스키마 사용 권한과 `private.check_auth_session()` 실행 권한을 추가해 정상 로그인을 복구했다. 이후 Supabase Auth의 원본 오류 응답에서 숫자 `code`가 문자열 `error_code`보다 먼저 선택되어 비밀번호 실패 RPC가 호출되지 않는 문제를 운영 로그로 확인했고, `error_code`를 먼저 읽도록 수정한 `auth-gateway`를 배포한 뒤 사용자가 로그인 제한 적용을 확인했다.

## ⑤ AI와 나

- AI가 한 일: 카드 1~4 문서와 소스를 대조하고, 인증 경계·소유권·세션 폐기·비밀값 비노출을 정리했다. 카드 5에서는 전체 자료 내보내기와 계정 삭제 경로를 연결하고 정적 검사를 추가했다. 로그인 공격 방어 단계에서는 Rate Limit·Turnstile·점진 제한의 배포 순서를 정리하고, Supabase 운영 로그에서 CAPTCHA Secret 불일치, `service_role` 권한 누락, 로그인 실패 코드 판별 오류를 구분했다.
- 내가 직접 판단한 일: 내 계정으로 5일 동안 실행 기록을 남기고, 2일차 뒤·3일차 앞에 우선순위 규칙 하나를 바꿨다. 실제 화면의 날짜별 기록과 합계를 직접 확인했다. 또한 Cloudflare와 Supabase에 Secret을 직접 등록하고, 운영 앱의 정상 로그인과 반복 실패 후 로그인 제한 적용을 확인했다.
- AI 제안을 따르지 않은 일: AI가 새 5일 구간을 다시 기록하자고 제안했지만, 실제로는 기존 5일 중 2일차와 3일차 사이에 규칙을 바꾼 상태였으므로 그 제안을 따르지 않고 기존 기록을 사용했다.

## ⑥ 아직 못 막은 것

운영 Supabase의 로그인·가입 Rate Limit 조정, Cloudflare Turnstile, 서버 측 점진 제한은 적용했다. 이 조합은 온라인 무차별 대입 공격의 속도와 비용을 높이지만, 이미 유출된 올바른 비밀번호를 사용하는 credential stuffing, CAPTCHA를 통과하는 공격, 분산 IP 공격까지 완전히 막지는 못한다.

2FA/MFA는 아직 구현하지 않았다. 이후 사용자가 TOTP를 등록하도록 하고, 등록 완료 전 다이어리 접근을 막으며, 화면뿐 아니라 JWT의 `aal2`를 PostgreSQL RLS에서도 요구해야 한다.

애플리케이션이 장기간 보관하는 별도 로그인 감사 로그도 아직 없다. Supabase 기본 Auth·Edge Function 로그와 `private.auth_login_throttle`의 제한 상태는 확인할 수 있지만, 성공 시 제한 행을 삭제하고 24시간 지난 실패 행도 정리하므로 영구적인 감사 이력은 아니다. 감사 로그를 추가할 때도 이메일·IP·비밀번호·token 원문은 저장하지 않고 이벤트 시각, 결과, 계정·IP HMAC, 제한 단계만 제한된 보존 기간으로 기록해야 한다.

## 1일차에 고정한 질문과 지표

- 질문: **“하루 동안 계획한 일을 실제 실행 기록으로 남긴 시간은 얼마인가?”**
- 지표: **하루 실제 실행 시간**
- 단위: **분/일**
- 계산: Asia/Seoul 달력 날짜별로 `task_execution_logs.actual_minutes`를 합산한다. 화면의 `See > 실제 시간`과 같은 자료를 사용한다.
- 주 시작 요일: **월요일**
- 반올림: 시작·종료 시각 차이를 분으로 바꿀 때 가장 가까운 정수로 반올림하고, 1분 미만은 1분으로 저장한다. 일평균은 소수 둘째 자리에서 반올림해 소수 첫째 자리까지 표시한다.
- 값이 빠질 때: 시작·종료 시각 또는 실제 시간이 없으면 그 실행 기록은 지표에서 제외하고, 해당 날짜의 합계는 남은 유효 기록의 합으로 계산한다.
- 중복될 때: 같은 할 일·같은 날짜라도 별도 실행 기록이면 각각 실제 수행 시간으로 합산한다. 동일 행을 다시 불러온 중복은 `id` 기준으로 한 번만 센다.
- 유난히 튈 때: 원자료를 삭제하거나 임의로 고치지 않고 `blocker_reason` 또는 회고에 이유를 남긴다. 사전에 정한 제외 기준이 없으므로 원자료 합계에는 포함하고, 전후 비교의 해석에서 별도 표시한다.

## 짧은 확인 방법

1. 어디로 가나요: `https://aleph-task-06.vercel.app/`로 간다.
2. 로그인 보호는 어떻게 확인하나요: Turnstile을 완료한 뒤 시험 계정에 틀린 비밀번호를 반복 입력해 로그인 제한 안내와 카운트다운을 확인하고, 허용 시각 뒤 올바른 비밀번호로 로그인한다.
